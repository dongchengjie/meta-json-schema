# Schema 表达惯例

本文件定义如何把已确认的源码事实写成 schema。审计方法见 `schema-maintenance.md`，仓库级边界以 `AGENTS.md` 为准。惯例与已确认的源码行为冲突时以源码为准。

## Schema 方言

项目使用 JSON Schema Draft-07，不使用后续草案的校验关键词。`markdownDescription`、`markdownEnumDescriptions`、`deprecationMessage` 等编辑器扩展没有 Draft-07 校验语义。

Draft-07 标准求值会忽略 `$ref` 的全部同级关键词。仅供现有编辑器展示的注解可沿用项目写法；必须生效的校验或条件通过 `allOf` 等 Draft-07 结构组合。

## 用户字段

写元数据之前先确认对象是不是用户字段。判定看用户会不会填写或选择这个键，不看它是否具名、是否独立成文件、有没有 `title`。

用户字段是解析模型 `properties` 里用户会填写或选择的键，并且该处直接给出这个键的输入形状。输入形状可以是 `type`、`enum`、`const`、组合，或指向标量、pattern、enum 的 `$ref`。这类字段必须具备形状关键词、`title`、`description` 和 `markdownDescription`；枚举值需要分别说明时再加 `markdownEnumDescriptions`。`default` 是否写入见「枚举与缺省」。

定义对象、`allOf` 分段、结构性节点、`if` / `then` / `else`、纯 `items`，以及只把另一个解析模型挂到某个键上的纯 `$ref`，都不是用户字段。它们只保留组合所需的形状和 `title`，不写 `description`、`markdownDescription` 或 `default`。`definitions` 里的转发 `$ref`、判别器同样不是用户字段。被条件组合包住的用户字段仍按用户字段写元数据。

旧字段缺元数据不是新字段的先例；也不得借「补全新字段」，给不是用户字段的对象补上用户字段才有的键。

## 解析模型、归属与顺序

Schema 单元对应公开输入的实际解析边界。字段、嵌入和分支属于直接读取它们的解析模型，不因后续转换、最终消费者、源码目录或内部类型拆分而改变归属；多个解析模型也不因转换成相同内部形状而合并。

`properties` 严格按解析模型的字段声明顺序排列。一个公开对象分阶段解码时，按实际解析阶段组合各模型，并保持每个模型内部顺序；分支模型分别保持自身顺序。转换结构、消费结构、物理文件顺序、字母顺序和主观分类都不是排序依据。历史顺序错误时只整理本次相关部分，避免无关重排。

解析模型的语义所有者决定文件和 definition 归属。独立嵌套或分支模型放在所有者 schema 中；自身是公开解析入口，或由多个入口直接解析的模型，提供稳定的根 schema 或具名 definition。Go 类型是否具名、结构大小、目录层级和复用次数不能单独决定拆分。

同一公开解析模型在多处出现时引用同一语义所有者；解析边界不同但形状相同的结构保持独立。跨文件只引用根 schema 或具名 definition，不引用 `allOf`、`properties` 等布局路径。公共标量、数组、pattern 和 enum 仅在语义一致时复用；对象共享还必须确认解析模型相同。

标量的 compatible 或严格 JSON 类型由实际解析方式决定，不按模块类别推断。对象、数组、结构性 `items`、判别值和条件组合按实际语义建模。

## 关键词布局

在保留 `$schema`、`$id` 等元标识及既有组合结构的前提下，对象依次放置 `type`、`title`、`definitions`、`required`、`properties` 和条件组合。用户字段先放形状关键词（`type`、`$ref`、`enum`、`const` 或组合），再放枚举说明、`title`、`description`、`markdownDescription`，最后放 `default` 等补充语义。定义对象、分段、纯 `$ref`、数组 `items`、判别器和条件内部沿用相邻文件的短写。

## 文案

写任何用户可见文案前，先确认对象是不是用户字段，再检索同名字段、同种单位、同种弃用声明，以及职责相同的最近实现。含义一致且都是用户字段时，复用术语、句式和元数据集合；含义不同则按当前语义另写。不得把用户字段的完整元数据套到定义对象或纯 `$ref` 上。协议名、缩写、单位及中英文格式以语义最近的当前实现为准。历史句式、产品层 merge schema 和条件互斥提示不能作为 Mihomo 核心配置新字段的先例。

`title` 写字段短名。`description` 写该字段自身含义，依据是最终消费者的赋值与分支。

某一类信息写进哪个关键词，以职责相同的现有用户字段为准，不要为某一类事实另立安放规则。旧 schema 文案、示例注释、结构体注释、日志标签和实现内部称呼只是线索；与消费者冲突时改描述。没有锁定实现依据的内容不得写入。

用户可见文案用「默认」陈述缺省行为，不用「省略时」或「省略后」。`default` 关键词何时写入、描述是否重复该值，见「枚举与缺省」。

曾经有效而后废弃的 Mihomo 公开字段使用 `deprecationMessage`，格式为 `v<当前未发布版本> 已弃用(...)`。括号内写取代方式或不再生效的行为；无补充说明时可不用括号。未发布版本号与 `CHANGELOG.md` 未发布章节标题一致。发布说明如何措辞见 `schema-maintenance.md`。

## 枚举与缺省

字段未出现与字段显式出现是两种不同的公开输入。审计如何区分这两条路径，见 `schema-maintenance.md`；本文件只规定它们如何进入 schema。

公开值域是最终消费者会保留并据以分支的已解析值，不是解析器为了读入而容忍的形状。枚举只列用户需要明确选择的这类值。未配置由缺省表达：可填值用 `default` 且描述不再重复该值；不可填的缺省行为只在描述里写「默认」，不写 `default`。

字段一旦出现，就必须符合其公开类型和上述值域。弱类型转换、空值回落、未知字段容忍或「未报错」只能说明解析没有失败，不能把错误类型、缺省哨兵或其他仅因宽容才通过的输入写成合法值。

下列情形不要互相套用：

- 消费者对同一合法类型的多个取值做稳定分支时，保留该类型；用说明写出分支，不要为了「收紧」改成只接受其中一条路径的 `const` 或单值枚举。
- 空字符串、数值零、`null`、空集合和空对象若只表示未配置、初始化或其他缺省哨兵，就不得写入 enum、`oneOf`、`default`、补全、示例，也不得在说明里写成用户可选值。只有源码证明它们被消费者区分并产生独立行为时，才可以显式建模；即使既有 schema 已经收录，也不能作为新增字段的先例。

按位置关联的枚举说明必须与枚举等长且顺序一致。

可选对象一旦出现，应满足激活该能力所需的完整约束；不能用空对象或缺少关键成员的半配置对象表示「关闭」或「沿用默认」。需要关闭能力时不要写这个字段或配置块，具体以最终消费者对未配置状态的行为为准。

`default` 只记录字段未配置时仍然成立、且用户可合法填写的值。它不授权填写内部零值或其他缺省哨兵。

## 条件与范围

只表达源码稳定要求或明确拒绝的关系，并沿用相邻实现的 Draft-07 表达。`properties` 不表示字段存在；条件仅应在字段出现时触发的，必须同时表达存在性。字段在某条执行路径中被忽略，不等于 schema 应禁止该组合。

除非维护者明确要求且项目已有相同约定，不因 Go 整数宽度、潜在异常或实现推测自行添加 `minimum`、`maximum` 等范围限制。新增条件或范围会扩大拒绝集合，必须验证正反例。

## 兼容与弃用

经源码或历史确认曾进入有效消费路径的公开配置，上游废弃或移除后仍保留其最后已知位置和输入校验，并按「文案」添加或更新 `deprecationMessage`。同步解除不再成立的 `required` 和条件要求，使当前推荐写法不受旧配置约束；`default`、补全和其他引导只采用当前推荐行为，示例不再使用弃用写法。

从未被支持或消费的误建模不适用兼容保留；排除旧版本行为和兼容别名后，按实际接口纠正。

## 惯例演进

新发现先记录为当前任务的审计结论。只有当前实现、相关历史和维护者确认共同支持时，才更新本文件。不得把一次性修复、单个协议特例、某次描述改写里遇到的信息种类，或未经验证的旧文档，写成通用安放规则。
