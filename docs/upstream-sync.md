# Mihomo 上游同步指南

本指南只定义上游同步特有流程。配置审计、示例、未发布 changelog 和验证见 `schema-maintenance.md`，表达方式见 `conventions.md`，仓库级边界以 `AGENTS.md` 为准。

同步必须先固定上游范围，再按顺序审计范围内每一条提交，并把影响本项目公开接口的提交映射为可线性追溯的本地提交。

## 维护上游副本

在操作系统临时目录维护 Mihomo `Alpha` 工作副本，不依赖开发者的其他项目目录。临时目录可能被清理、下载可能中断、仓库也可能被外部修改，因此每次使用前都要验证仓库身份、origin、分支、对象和工作树，不能把缓存存在本身视为同步状态。

1. 缓存不可用时在新的候选目录 clone；仅在 clone 完成且验证通过后启用，不覆盖来源不明或不完整的残留目录。
2. 已有缓存的 origin 必须为 `https://github.com/MetaCubeX/mihomo.git`，当前分支必须为 `Alpha`，且工作树干净；任一项不符时停止，不清理或强制重置。
3. 更新前先成功获取远端 `Alpha`，再 fast-forward 本地分支；任一步失败都不得把旧 HEAD 当作最新状态继续。
4. 已固定范围的对象完整存在时可离线审计；对象缺失时重新获取相同对象，无法恢复则停止，不静默替换范围。

网络操作按执行环境申请授权。遇到 dubious ownership 时，只为必要的单条命令临时声明安全目录，不修改全局 Git 配置。

## 确定同步范围

综合本仓库提交历史、工作树 diff、schema、示例和 changelog 判断已同步位置，并识别开发者已手工完成的部分。版本号、tag、changelog 或提交标题都不能单独作为已同步基线。

起点是已同步位置之后的第一条上游提交。终点按下列顺序确定：

1. 用户明确给出的终点（提交或 tag）。
2. 用户只说「同步上游」或同等含糊表述时：以当前 `Alpha` HEAD 为终点，纳入已同步位置之后的全部提交。

不要自行改用更近的 tag 或截断范围。工作过程中 `Alpha` 若继续前进，不得把新提交并入已固定范围。

范围确定后，先向用户报告已同步位置、终点完整 hash，以及终点若为 tag 时的名称，再开始逐提交审计。用户当场给出不同终点时，改用该终点并重新报告。

起止点记录完整 hash。后续计数、日志、diff 和源码读取只使用这些 hash，不依赖移动分支。每个审计阶段确认缓存身份、干净工作树和对象可读性；缓存丢失时重新取得并验证相同对象。

按固定范围的实际提交数逐条读取完整 diff，不凭标题判断影响。合并提交应结合各父提交与最终合并结果审计，不能依赖默认日志展示判断其无影响。

## 逐提交审计

对每条提交按 `schema-maintenance.md` 追踪公开输入、解析模型、消费路径和横向影响，并检查目标范围内同一数据流的后续修改。后续提交若重命名、放宽、回滚或修正了同一接口，仍按上游顺序分别映射。每一条本地提交只反映其对应上游提交之后的公开接口；不得跳过后续修正，也不得把已被推翻的中间态写进更晚的提交。

`go.mod`、`go.sum` 及等价锁定清单的变化与 Mihomo 源码变化同等对待。先判断被升级模块是否进入公开配置数据流。相关则读取该上游提交锁定的精确版本，按 `schema-maintenance.md` 比较升级前后的各项。下列事实均不能单独作为跳过依据：Mihomo 自身文件未改、标题为依赖升级、未知字段未报错、仅文档或示例发生变化。

依赖源码以对应上游提交锁定的版本为准。可只读使用本机已有模块缓存；缺失时将任务下载的精确版本放在系统临时目录。不得以依赖仓库的移动分支替代锁定版本。只有完成上述比较并确认无公开接口影响后，才记录为跳过。

## 提交映射

一条有公开接口影响的上游提交，对应一条本地提交，并保持上游顺序。该本地提交必须一次交付当时完整的发布视图：schema、受影响示例，以及按 `schema-maintenance.md` 写就的未发布 changelog。无影响的提交不创建空提交。

上游后来又修正同一接口时，仍对应新的本地提交；未发布 changelog 按 `schema-maintenance.md` 改写。只有本地写错、漏写或表达不符合惯例时，才用 fixup/autosquash 折回引入该变化的映射提交，不在映射序列末尾另开只含修正的提交。

一行标题遵循本仓库约定式提交历史，只描述本项目实际公开接口。schema 仍保留该字段时，不得写成删除或丢弃；上游类型名、内部实现、对外口吻和 PR 编号都不是标题来源。正文只包含 `Upstream-Commit: <完整 40 位 hash>` trailer。每次只暂存该提交涉及的显式路径，并在提交前核对暂存边界。

映射序列只包含上述发布视图。本次同步若改写代理流程文档，放在映射序列之后的独立 `docs` 提交，不并入最后一条映射。

## 交付

除 `AGENTS.md` 的通用交付内容外，还应报告：

- 实际采用的上游范围：已同步位置、终点 hash，以及终点若为 tag 时的名称
- 本地提交与上游 hash 的映射
- 跳过提交的分类和源码依据
- 建议手动 tag 的已完整审计范围终点 hash

除非用户明确要求，不创建 tag 或发布提交。
